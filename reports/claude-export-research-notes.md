## 二、核心研究对话："评估技能而非代理的持续评估方法"（2026-10-08 → 10-12，18 条消息）

这是本项目实验设计的主要出处，按时间线：

### 1. ACES 论文总结（NVIDIA，arXiv:2608.20614）
- 仓库原生评测框架：配对实时试验（同任务/模型/沙箱，有无 skill 各跑一次）、Skill Lift（有 skill 得分 − 无 skill 得分）、ATIF 轨迹格式、六项运行时指标
- 主要结果：64 个生产 skill 中 58 个、4 种 harness、947 个有效配对，平均综合 Skill Lift 0.2134（95% CI [0.1967, 0.2301]）；仅看结果增益 0.1799；72.8% 配对为正
- 结构检查与 LLM 评审 Spearman 相关仅 0.14 —— 静态扫描测不出运行时价值
- 相关论文旁证：AEVAL（执行者/评分者分离，防自评偏差）、OpenSkillEval（agent 平均仅 48% 情况会主动读 skill；许多热门 skill 不优于基线）

### 2. ACES 对 vista 的四点帮助
1. Skill Lift 可直接用作对照实验：flat vs PD 配对跑，净收益 = PD vs flat 的分差
2. 静态检查测不出披露策略好坏 → 需要轨迹级评测
3. 轨迹级指标适合观察披露行为 → 披露专属指标：披露准确率、披露冗余度（token 浪费）、漏披露率、转换保真度
4. OpenSkillEval 的"agent 常常不读 skill"可作为动机引用

### 3. 实验设计（vista 实验方法的雏形）
- 三组对照：无 skill / 原始 flat skill / vista 的 PD 版本；两个 lift：PD vs 无 skill（skill 价值）、PD vs flat（净收益——"你最需要证明的数字"）
- 消融：去反馈信号改随机/全披露、不同反馈来源、不同 PD 粒度
- AEVAL 风险提示：agent 自己判断反馈、自己披露、自己评分会高估效果 → 评分者与执行者分离、按首尝试结果评分、单独记录披露带来的修正（**即后来 noskill-retry 控制组的由来**）

### 4. Token 消耗排查建议（早期"效果不好"的诊断）
- 拆分 token 构成：按轮次记录输入/输出/缓存命中；多轮披露会反复累积上下文并破坏前缀缓存
- **核心原则："披露只追加，不改动前缀"** —— 披露用工具结果追加到对话末尾，第 0 层固定在前缀，已披露状态放外部记录不回写前缀，设缓存断点，避免重复披露，批量清理
- 算"每次成功的 token 成本"而非总 token
- 检查 skill 本身长度：skill 短则 PD 转换开销是净成本
- flat 版本整个 skill 在前缀只需缓存一次——只比原始 token 数会不公平放大 PD 成本（**即后来 skill_read_tokens 计数修正的由来**）

### 5. 第 0 层目录设计建议
- 描述写"什么时候用"而非"是什么"（触发条件明确，减少漏披露/过度披露）
- 目录带大小信息（约多少 token）；目录要自足（保留关键步骤骨架）
- 明确"必读"与"按需"；条目数个位数到十来个；验证方法：按条目统计"该开没开"和"开了没用"

### 6. SkillJuror 论文（arXiv:2606.11543，2026-06-10，代码开源）—— 与 vista 高度重合
- 渐进披露 vs 归一化 flat 基线（语义受控变体、配对多次试验、轨迹证据），SkillsBench 82 任务
- 结果：每轨迹接触 skill 资源数 1.18 → 3.85，有效采纳事件 1.33 → 3.92；410 次配对试验 PD 多通过 17 次（+4.1%）；收益依赖任务（指导实现/检查/修复时有效；严格输出格式、数值阈值、长产物流水线时弱）
- **对 vista 的解释**：总体收益本来就小（+4.1%），每组 3 次的样本量容易被噪声淹没
- **差异化点：SkillJuror 的 PD 是静态的（根文件指向资源，agent 自行决定读取）；vista 是反馈驱动披露——这是 SkillJuror 没覆盖的部分，可作为贡献点**（即本项目 sj4 协议的立论）

### 7. vista 测试任务筛选标准
1. skill 体量大（几千 token 以上，有"只在特定步骤才需要"的内容）
2. skill 对任务有正向增益（排除负增益任务）
3. 多步骤任务（不同阶段需要不同知识）
4. 难度分层抽样（中等到较难）
5. 优先高增益领域
- 操作：统计每个任务 `environment/skills/` 的 skill 总 token 数，结合已有结果按"体量大且增益为正"排序
